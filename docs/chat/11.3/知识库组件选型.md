# 知识库组件选型决策

- 日期：2026-11-03
- 状态：已决定，待落地
- 涉及文件：`app/agent/main.py`（Agent 服务入口）、`app/core/config.py`（新增配置项）
- 运行环境：Python 3.14 / `agentscope[service,storage-redis]==2.0.11`

> 部分决策已被 [`实施方案.md`](./实施方案.md) 覆盖并以实施方案为准：`QDRANT_URL` 改为**必填、无 `path` 回退**；`KB_PUBLIC_OWNER` / `KB_PUBLIC_IDS` 改为**硬编码**；embedding 端点已验证可用。

## 一、决策摘要

知识库**不引入第三方 RAG 服务**，直接使用 AgentScope 内置的知识库子系统（`agentscope.app.rag` + `agentscope.rag`），向量库选 **Qdrant**：

| 决策项 | 取值 |
|---|---|
| 接入方式 | 框架内置：`create_app(knowledge_base_manager=...)`，不自己写上传/索引/检索 |
| 隔离策略 | **一人一库**（`CollectionPerKbManager`，collection-per-KB），归属由 storage 的 `user_id` 强制 |
| 公共知识库 | 系统账号持有 + `ResourceAccessPolicy` 向所有用户下发 **READ** 引用，不复制数据 |
| 向量库 | `QdrantStore`（首期 `path` 进程内模式，保留 `url` 升级路径） |
| Embedding | 百炼 `text-embedding-v4`（1024 维、8192 上下文） |
| 原件存储 | `LocalBlobStore` → `<data_root>/blobs`（索引后不删，删文档/删库才释放） |
| 索引 | `enable_index_worker=True`，索引跑在 API 进程内 |
| 检索 | `RAGMiddleware`，默认 `agentic`（暴露 `search_knowledge` 工具），参数随 session 下发 |
| 身份 | 主 API 代理，注入 `X-User-ID`；agent 端口不对外 |
| 元数据存储 | 复用现有 `RedisStorage`（DB1），不改 PG 表结构 |

一句话：**框架内置 + collection-per-KB 做用户隔离 + 系统账号放公共库 + Qdrant 做向量存储**。

## 二、背景

当前知识库能力为零，但教学场景已经明确有两类资料：

- **个人库**：学生自己上传的笔记、作业、错题整理，彼此不可见；
- **公共库**：课程大纲、教材、课件、实验手册，全员可检索、只有管理员能改。

`app/agent/main.py` 目前只接了 storage / message_bus / workspace，`create_app()` 的 KB 相关参数全部为空，`enable_index_worker=False`。AgentScope 2.0.11 已经内置了完整链路（文档表、blob 存储、解析、切块、索引 worker、KB HTTP 路由、`RAGMiddleware`），不需要从零实现。

## 三、约束

1. 个人库必须**按用户物理隔离**，不能靠 prompt 约束。
2. 公共库**只读**，普通用户不得修改、删除。
3. 单机部署，尽量少加常驻服务（现有 PG + Redis 两个容器）。
4. 复用现有百炼 key 与 `data_root` 持久目录，不新增云资源。
5. 不把学生上传的原始文件传到第三方 RAG 平台。

## 四、候选方案与排除理由

| 方案 | 结论 | 理由 |
|---|---|---|
| **A. 框架内置 KB（collection-per-KB）** | **采用** | 上传/解析/切块/索引/检索/路由全部现成，隔离由 storage 强制 |
| B. 只借 `KnowledgeBase` / `RAGMiddleware`，元数据自管 | 排除 | 上传、索引状态机、失败重试要重写一遍，本质是把 `agentscope.app.rag` 复制一份 |
| C. 外部 RAG（百炼知识库 / RAGFlow / Dify） | 排除 | 按用户隔离要么一用户一索引，要么依赖供应商 tag；数据出境；引用样式难与题目体系对齐 |
| D. 单 collection + `metadata_filter` | 暂不采用 | 需要自定义 `KnowledgeBaseManagerBase`；filter 写错即越权，而当前规模用不上物理混布带来的收益 |

补充说明：

- **B 的变体（pgvector）**：项目已有 PG 17，理论上是组件最少的路线，但 AgentScope 没有 `VectorStoreBase` 的 pgvector 实现，需要自己写适配器并维护 HNSW 索引；等 Qdrant 成为瓶颈时可以再评估。
- **Milvus Lite**：嵌入式、wheel 仅 24MB、检索比 Qdrant 本地模式快，但过滤能力弱、`milvus-lite>=3.1.0` 的平台与版本安装风险更高；Qdrant 的优势是 `path` 与 `url` 两种形态共用同一份代码。
- **D 的适用场景**：用户量到几千、collection 数量成为负担时，再改成“一个用户一个 collection + `metadata_filter={'kb_id': ...}`”，接口层不变。

## 五、关键设计决策

### 5.1 隔离模型：一人一库

- 每个 KB 在向量库占一个 collection，命名 `kb_<uuid>`，**不编码 user_id**；归属关系只存在 storage 的 `KnowledgeBaseRecord.user_id` 上。
- 所有 `list/get/update/delete` 都是 owner-scoped，别人拿不到记录，也无法解析出 runtime handle。
- 好处：删库即 drop collection，干净；每个库独立维度、独立切块配置、独立重建；不存在 filter 漏写导致的越权。
- 代价：collection 数 ≈ 用户数 × 每用户库数，需要监控；本地 `path` 模式下所有 collection 都在同一进程内存里。

### 5.2 公共库 = 授权，不是复制

公共库建在一个专用系统账号（`KB_PUBLIC_OWNER`，例如 `system`）下，通过 `ResourceAccessPolicyBase` 给所有 viewer 下发引用：

```python
ResourceRef(
    kind=ResourceKind.KNOWLEDGE_BASE,
    owner_id="system",
    resource_id="<公共库 id>",
    permission=ResourcePermission.READ,
)
```

- session 挂载 KB 时会走 `access.get_resource(...)` 校验（`_router/_session.py::_ensure_knowledge_bases_exist`），policy 授权后公共库才能被任意用户挂进会话。
- **只能发 READ**：上传/删除走 `_service/_knowledge_base.py::_require_edit`，给 EDIT 等于把公共库的增删权交给所有用户（EDIT 是准 co-owner，连 `delete_knowledge_base` 都能过）。
- 系统账号同时持有公共库的 embedding credential，普通用户不需要为公共库准备 key。
- 公共库 id 走配置（`KB_PUBLIC_IDS`），换库只改环境变量，不改代码。

### 5.3 embedding 凭证归属（硬约束）

`CollectionPerKbManager.get_knowledge()` 解析 embedding 模型时，是**按 KB 的 owner 直接读 storage**（`_collection_per_kb.py` 注释："the credential lives under the same owner as the knowledge base"）。这意味着 **`credential_id` 必须和 KB 同 owner**，跨 owner 共享 credential 建库会在运行时报 `KnowledgeBaseNotFoundError`。

因此采用：

| 库类型 | owner | credential |
|---|---|---|
| 个人库 | 用户本人 | 用户注册时由主 API 在 agent 侧创建 `dashscope_credential`（同一把 key） |
| 公共库 | `system` | 系统账号一份 |

代价：key 在 Redis 里按用户复制 N 份，轮换时要批量更新；换来的是个人库天然隔离、**不需要** `user_id → kb_id` 映射表。

> 备选：所有 KB 都归 `system`，用 policy 按用户下发 EDIT，再用 PG 存映射表。省掉 key 复制，但多一张表 + 一套创建/删除逻辑，暂不采用。

### 5.4 向量库形态：先 `path`，后 `url`

| 形态 | 进程 | 并发 | 检索 | 结论 |
|---|---|---|---|---|
| `QdrantStore(path=...)` | 无（进程内） | **单进程独占文件锁** | 纯 Python + numpy 暴力扫描 | **首期采用** |
| `QdrantStore(url=...)` | 1 个容器 | 多进程/多副本 | Rust HNSW | 拆 worker / 多副本时切换 |

- `path` 模式底层是 qdrant-client 的 `QdrantLocal`（SQLite 持久化），源码自述 "Use for small-scale data, demos, and tests"；数据全量常驻内存，1024 维 float32 约 4KB/chunk。
- 量级估算：一本教材 ≈ 3000 chunk ≈ 12MB；100 个学生各 1000 chunk ≈ 400MB，`path` 模式可接受。
- 切换 `url` 时代码只改 `build_vector_store()` 一个分支，但**数据不会自动迁移**，需要从 blob 重新索引。
- `path` 模式下**不能**再起独立索引 worker，也不能 `uvicorn --workers > 1`，否则第二个进程抢不到文件锁。

### 5.5 原件存哪：LocalBlobStore

- 只存**原始字节**，不参与解析/切片/向量化；URI 形如 `local://kb/<kb_id>/<doc_id>`。
- 上传按 1 MiB 分块落盘，索引 worker 再流式读回，保证大文件不进内存。
- **索引成功后不删除**：保留原件用于重建索引与原文预览/下载；只有删文档或删 KB 时才 best-effort 清理，磁盘占用 ≈ 已上传原件总和。
- 必须显式传绝对路径 `<data_root>/blobs`，不要用默认的 `./blobs`（跟随 cwd）。
- 单机可用；未来多副本或独立 worker 时换 `S3BlobStore`（COS 兼容 S3 协议）。

### 5.6 索引与解析

- `enable_index_worker=True`：API 进程内启动 `IndexWorker` + `IndexSweeper`，上传后异步索引，文档状态 `pending → processing → ready/failed`。
- 解析器默认只有 `TextParser`，必须显式注册，否则 PDF 无法解析：

```python
[TextParser(), PDFParser(), WordParser(), PPTParser()]
```

- `pypdf` 是 agentscope 的 core 依赖，已装；`python-docx` / `python-pptx` 需要单独加。
- **不要**直接装 `agentscope[rag]`：会带 `pandas` / `xlrd` / `openpyxl`，而当前不需要 Excel 解析。

### 5.7 检索模式

`RAGMiddleware` 两种模式，通过 session 的 `knowledge_config.parameters.mode` 控制：

| mode | 行为 | 成本 |
|---|---|---|
| `agentic`（默认） | 只暴露 `search_knowledge` 工具，模型自己决定何时检索 | 按需 |
| `static` | 每轮用户输入自动检索并注入 | 每轮固定一次 |

- 默认 `agentic`：教学场景里大量对话不需要查资料，避免每轮都打 embedding。
- 可调参数：`top_k`、`score_threshold`、`rerank_candidate_k`、`emit_hint_event`、`persist_hint`、`hint_template`。
- 同时挂个人库 + 公共库时，middleware 会 fan-out 到所有 KB，按 `(document_id, chunk_index)` 去重后取 top_k。

### 5.8 拓扑与身份

- KB 路由挂在 agent 服务上，前缀 `/knowledge_bases`。
- agent 服务的身份来源是**明文请求头 `X-User-ID`**（`agentscope/app/deps.py::get_current_user_id`），没有签名校验。
- 因此前端**不能直连** agent 端口：主 API 校验 JWT 后，带 `str(user.id)` 转发；agent 服务只监听内网。
- 兑换数据时注意 ID 类型：主 API 是 `uuid.UUID`，透传时统一 `str(uuid)`。

### 6.1 配置（`app/core/config.py`）

class Settings(_Base):
    # ... 现有字段
    qdrant_url: str | None = None          # 留空 = 进程内 path 模式

### 6.2 装配（建议新增 `app/agent/knowledge.py`）

```python
from agentscope.app.access import (
    ResourceAccessPolicyBase,
    ResourceKind,
    ResourcePermission,
    ResourceRef,
)
from agentscope.app.rag import CollectionPerKbManager, LocalBlobStore
from agentscope.app.storage import StorageBase
from agentscope.rag import PDFParser, PPTParser, QdrantStore, TextParser, WordParser

from app.core.config import Settings


class TeachingAccessPolicy(ResourceAccessPolicyBase):
    """公共库对所有用户只读;个人库走 storage 的 owner 隔离,不在此出现。"""

    def __init__(self, owner_id: str, public_kb_ids: list[str]) -> None:
        self._refs = [
            ResourceRef(
                kind=ResourceKind.KNOWLEDGE_BASE,
                owner_id=owner_id,
                resource_id=kb_id,
                permission=ResourcePermission.READ,
            )
            for kb_id in public_kb_ids
        ]

    async def list_accessible(self, viewer_id, kind, storage):
        if kind is not ResourceKind.KNOWLEDGE_BASE:
            return []
        return list(self._refs)


def build_vector_store(settings: Settings) -> QdrantStore:
    """有 QDRANT_URL 走服务端;否则进程内落盘(单进程)。"""
    if settings.qdrant_url:
        return QdrantStore(url=settings.qdrant_url)
    return QdrantStore(path=str(settings.qdrant_path))


def build_knowledge_base_manager(
    settings: Settings,
    storage: StorageBase,
) -> CollectionPerKbManager:
    return CollectionPerKbManager(
        storage=storage,
        vector_store=build_vector_store(settings),
    )


def build_blob_store(settings: Settings) -> LocalBlobStore:
    return LocalBlobStore(root_dir=str(settings.kb_blobs_dir))


def build_parsers() -> list:
    return [TextParser(), PDFParser(), WordParser(), PPTParser()]


def build_access_policy(settings: Settings) -> TeachingAccessPolicy:
    return TeachingAccessPolicy(settings.kb_public_owner, settings.kb_public_ids)
```

  - `<data_root>/qdrant/`（`path` 模式下的向量数据）

## 八、风险与未决项

| # | 风险 | 说明 | 处理 |
|---|---|---|---|
| 1 | `X-User-ID` 可伪造 | agent 服务只做明文头读取，无签名 | 只监听内网；主 API 代理；禁止前端直连 |
| 2 | embedding 端点未验证 | `LLM_BASE_URL` 是百炼 MaaS 专属域名，不保证提供 `/embeddings` | 落地第一步先打一次 `text-embedding-v4`；不通则单独申请 DashScope key 或本地 Ollama bge-m3 |
| 3 | key 按用户复制 | 每人一份 `dashscope_credential`，轮换需批量更新 | 封装 `rotate_embedding_credential()`；或在规模化后改系统账号 + 映射表 |
| 4 | `path` 模式单进程 | 独占文件锁，独立 worker / 多副本 / `--workers > 1` 会启动失败 | 部署固定单 worker；扩展前切 `QDRANT_URL` |
| 5 | `path` 模式性能 | 纯 Python 暴力扫描，无 HNSW | 控制规模；chunk 上到十万级或并发升高即切服务端 |
| 6 | blob 不自动清理 | 原件常驻磁盘，删文档/删库才释放 | 纳入磁盘告警；定期核对孤儿文件 |
| 7 | 配置钉死 | embedding 模型、维度、chunker 创建后不可改 | 换模型 = 新建库 + 重新索引；UI 上弱化“修改”入口 |
| 8 | 元数据与业务割裂 | KB 记录在 Redis DB1，用户/题目在 PG | Redis 保持 AOF（已开）；统计走 agent 接口或定期同步 |
| 9 | collection 数量 | 一人一库，规模随用户线性增长 | 监控 `/collections` 数量；阈值后评估方案 D |
| 10 | 索引失败无告警 | 失败只落到文档状态 `failed` | 增加状态巡检任务，失败文档在 UI 可见并可重试 |
| 11 | 公共库权限配置错误 | policy 误发 EDIT 会让普通用户可删公共库 | `TeachingAccessPolicy` 中写死 READ；加单测断言 permission |

## 九、验收标准

1. 学生 A 建库并上传 PDF，索引完成后文档状态为 `ready`，`<data_root>/qdrant` 与 `<data_root>/blobs` 下出现对应数据。
2. A 在会话中挂载自己的库，提问能被检索命中；学生 B 用相同问题检索不到 A 的内容。
3. 公共库对所有用户可见、可检索；普通用户调用修改/删除接口返回 403。
4. 同一会话同时挂载个人库与公共库时，一次检索能合并两库结果并去重。
5. 服务重启后，KB 列表、文档状态、向量检索结果均保持（`path` 模式落盘）。
6. 删除文档后，向量记录与 blob 文件同时被清理；删除 KB 后 collection 被 drop。
7. 上传不支持的类型或损坏文件时，文档状态为 `failed`，不影响其他文档。
